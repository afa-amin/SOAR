# پروژه SOAR مبتنی بر Wazuh

سامانه‌ای برای شناسایی، همبسته‌سازی و پاسخ خودکار به تهدیدات امنیتی، مبتنی بر Wazuh، Suricata، ModSecurity و پلتفرم Shuffle SOAR. این پروژه ترافیک شبکه و لایه وب را به‌صورت هم‌زمان پایش می‌کند، رخدادها را همبسته‌سازی می‌کند، پاسخ فعال (Active Response) اجرا می‌کند و نتیجه را از طریق Shuffle به کانال‌های اطلاع‌رسانی ارسال می‌نماید.

## معماری کلی

جریان کار سامانه به شرح زیر است:

1. **لایه تشخیص:** Suricata ترافیک شبکه را در حالت IDS پایش می‌کند و ModSecurity به همراه مجموعه قوانین OWASP CRS، درخواست‌های HTTP را در سطح وب‌سرور بررسی می‌کند.
2. **لایه جمع‌آوری و همبسته‌سازی:** رخدادهای Suricata و ModSecurity توسط Wazuh Manager جمع‌آوری شده و با استفاده از قوانین سفارشی (`local_rules.xml`) با یکدیگر همبسته می‌شوند تا حملات چندمرحله‌ای یا حملات ترکیبی شناسایی شوند.
3. **لایه پاسخ خودکار:** بر اساس شناسه قوانین فعال‌شده، Wazuh یکی از اسکریپت‌های Active Response (مسدودسازی IP، محدودسازی نرخ ترافیک یا ارسال اطلاعات به Shuffle) را اجرا می‌کند.
4. **لایه Orchestration:** پلتفرم Shuffle با دریافت وب‌هوک از اسکریپت‌های پاسخ فعال، فرایندهایی مانند استعلام IP از AbuseIPDB، اسکن فایل با VirusTotal، استعلام URL با Urlscan و اطلاع‌رسانی از طریق Bale و Telegram را به‌صورت خودکار اجرا می‌کند.
5. **لایه پایش:** یک سرویس Flask ساده، پوشه‌ای را برای بارگذاری فایل فراهم می‌کند که توسط Wazuh پایش شده و در صورت بارگذاری فایل جدید، فرایند اسکن بدافزار آغاز می‌شود.

## ساختار فایل‌ها

| فایل | دسته | توضیح |
|---|---|---|
| `ossec.conf` | پیکربندی Wazuh | فایل اصلی پیکربندی Wazuh Manager؛ شامل تعریف دستورات Active Response، نگاشت هر دستور به شناسه قوانین (`rules_id`)، زمان انقضای بلاک‌ها و پایش لاگ‌های سیستم |
| `local_rules.xml` | قوانین Wazuh | قوانین سفارشی برای تشخیص SYN Flood، DDoS حجمی، حملات وب (SQLi، XSS، Command Injection، SSRF، Webshell) و قوانین همبسته‌سازی برای شناسایی حملات چندبرداری |
| `suricata.yaml` | پیکربندی Suricata | پیکربندی موتور Suricata شامل تعریف شبکه‌های HOME_NET و EXTERNAL_NET و مسیر بارگذاری قوانین |
| `suricata.rules` | قوانین Suricata | قوانین سفارشی تشخیص SYN Flood، DDoS حجمی، SQL Injection، Command Injection، XSS، SSRF و دسترسی به Webshell |
| `crs-setup.conf` | پیکربندی ModSecurity | فایل پیکربندی OWASP Core Rule Set برای فایروال لایه کاربرد وب |
| `block-ip.py` | اسکریپت Active Response | مسدودسازی دائم آدرس IP مهاجم از طریق iptables، با پروتکل handshake استاندارد Wazuh (`check_keys`) |
| `rate-limit.py` | اسکریپت Active Response | اعمال محدودیت نرخ درخواست (پیش‌فرض ۵ درخواست بر ثانیه با burst ۱۰) روی IP مشکوک به‌جای مسدودسازی کامل |
| `send-ip-to-shuffle.sh` | اسکریپت Active Response | استخراج IP مبدأ و اطلاعات قانون فعال‌شده و ارسال آن به وب‌هوک Shuffle جهت استعلام از AbuseIPDB |
| `send-url-to-shuffle.sh` | اسکریپت Active Response | استخراج URL درخواست مشکوک و ارسال آن به وب‌هوک Shuffle جهت استعلام از Urlscan |
| `send-file-to-shuffle.sh` | اسکریپت Active Response | بارگذاری فایل جدید در VirusTotal، پایش وضعیت اسکن و ارسال نتیجه نهایی به Shuffle و Bale |
| `app.py` | سرویس کمکی | سرویس Flask جهت بارگذاری فایل در پوشه پایش‌شده توسط Wazuh (`/var/wazuh_monitor`) |
| `sendIpTesting.log` | تست | نمونه دستور شبیه‌سازی رخداد برای آزمایش `send-ip-to-shuffle.sh` |
| `sendUrlTesting.log` | تست | نمونه دستور شبیه‌سازی رخداد برای آزمایش `send-url-to-shuffle.sh` |

## گردش‌کارهای Shuffle

سه گردش‌کار مستقل در Shuffle برای پردازش خروجی اسکریپت‌های Active Response طراحی شده است:

**گردش‌کار File:** دریافت وب‌هوک، استعلام شناسه آنالیز از VirusTotal، دریافت جزئیات نتیجه اسکن و ارسال گزارش نهایی به Bale.

**گردش‌کار IP:** دریافت وب‌هوک، استعلام IP از AbuseIPDB، دریافت موقعیت جغرافیایی IP و توزیع نتیجه به‌طور هم‌زمان به Bale، ربات Telegram (SocleBot)، Zoho و سرویس Ntfy.

**گردش‌کار URL:** دریافت وب‌هوک، استعلام از Urlscan جهت تحلیل رفتار URL و ارسال نتیجه به دو ربات Telegram جداگانه.

علاوه بر گردش‌کارهای فوق، یک داشبورد اختصاصی در Wazuh برای نمایش یکپارچه رخدادها، حملات شناسایی‌شده و وضعیت پاسخ‌های فعال ساخته شده است.

## پیش‌نیازها

- سرور Linux با دسترسی root و ابزار iptables فعال
- Wazuh Manager و Wazuh Agent نصب‌شده و پیکربندی‌شده
- Suricata با پشتیبانی از EVE JSON و ادغام با Wazuh
- وب‌سرور مجهز به ModSecurity و مجموعه قوانین OWASP CRS
- Python 3 و Flask برای اجرای سرویس بارگذاری فایل
- حساب کاربری فعال در Shuffle، VirusTotal، AbuseIPDB و Urlscan
- ربات‌های پیام‌رسان Bale و Telegram با توکن معتبر

## مراحل استقرار

1. **نصب Wazuh Manager:** Wazuh را بر اساس مستندات رسمی نصب و راه‌اندازی کنید.
2. **استقرار قوانین سفارشی:** فایل `local_rules.xml` را در مسیر `/var/ossec/etc/rules/` قرار داده و Wazuh Manager را راه‌اندازی مجدد کنید.
3. **پیکربندی Suricata:** فایل‌های `suricata.yaml` و `suricata.rules` را در مسیرهای متناظر Suricata (معمولاً `/etc/suricata/`) قرار داده، مقادیر `HOME_NET` و `HTTP_SERVERS` را متناسب با شبکه خود تنظیم و سرویس Suricata را ادغام کنید تا لاگ EVE JSON آن توسط Wazuh پردازش شود.
4. **پیکربندی ModSecurity:** فایل `crs-setup.conf` را در مسیر نصب OWASP CRS قرار داده و ماژول ModSecurity را روی وب‌سرور فعال کنید.
5. **استقرار اسکریپت‌های Active Response:** فایل‌های `block-ip.py`، `rate-limit.py`، `send-ip-to-shuffle.sh`، `send-url-to-shuffle.sh` و `send-file-to-shuffle.sh` را در مسیر `/var/ossec/active-response/bin/` کپی کرده و مجوز اجرا (`chmod +x`) به آن‌ها بدهید.
6. **پیکربندی نهایی Wazuh:** فایل `ossec.conf` را جایگزین یا با پیکربندی فعلی ادغام کنید تا دستورات و بلوک‌های `active-response` فعال شوند، سپس سرویس Wazuh Manager را راه‌اندازی مجدد کنید.
7. **راه‌اندازی سرویس بارگذاری فایل:** فایل `app.py` را روی سرور اجرا کرده و اطمینان حاصل کنید مسیر `/var/wazuh_monitor` توسط Wazuh FIM پایش می‌شود.
8. **پیکربندی Shuffle:** سه گردش‌کار File، IP و URL را طبق تصاویر پروژه در Shuffle بسازید و آدرس وب‌هوک هرکدام را در اسکریپت‌های متناظر جایگزین کنید.
9. **تنظیم کلیدهای API:** کلیدهای VirusTotal، AbuseIPDB، Urlscan و توکن‌های Bale/Telegram را به‌صورت متغیر محیطی یا در بخش‌های مربوط به Shuffle تنظیم کنید (نه به‌صورت مستقیم در کد؛ به بخش هشدارهای امنیتی مراجعه کنید).
10. **بررسی نهایی:** با ارسال ترافیک آزمایشی، صحت عملکرد کل زنجیره از تشخیص تا اطلاع‌رسانی را تأیید کنید.

## آزمایش سامانه

برای آزمایش مستقل هر اسکریپت بدون نیاز به تولید ترافیک واقعی، می‌توان رخداد شبیه‌سازی‌شده Wazuh را مستقیماً به اسکریپت ارسال کرد:

```bash
echo '{"version":1,"origin":{"name":"node01","module":"wazuh-analysisd"},"command":"add","parameters":{"alert":{"rule":{"id":"100033","description":"Test SQL Injection Alert"},"data":{"srcip":"8.8.8.8"}}}}' | sh send-ip-to-shuffle.sh
```

نمونه مشابه برای آزمایش گردش‌کار URL نیز در فایل `sendUrlTesting.log` موجود است. خروجی هر دو اسکریپت در فایل `/var/ossec/logs/active-responses.log` ثبت می‌شود و برای عیب‌یابی قابل بررسی است.

## نکات و هشدارهای امنیتی

پیش از انتشار عمومی این مخزن یا استقرار در محیط تولید، موارد زیر باید اصلاح شوند:

- در فایل `send-file-to-shuffle.sh` کلید API واقعی VirusTotal و توکن ربات Bale به‌صورت متن ساده در کد قرار دارند. این مقادیر باید حذف و به متغیرهای محیطی یا یک فایل پیکربندی خارج از کنترل نسخه (git-ignored) منتقل شوند.
- آدرس‌های وب‌هوک Shuffle در اسکریپت‌ها به‌صورت مستقیم درج شده‌اند؛ پیشنهاد می‌شود این مقادیر نیز از طریق متغیر محیطی خوانده شوند تا امکان استفاده مجدد از کد در محیط‌های مختلف بدون افشای زیرساخت فراهم شود.
- سرویس `app.py` با `debug=True` و روی آدرس `0.0.0.0` اجرا می‌شود که برای محیط تولید مناسب نیست؛ توصیه می‌شود در استقرار نهایی این پرچم غیرفعال و سرویس پشت یک WSGI Server مناسب (مانند Gunicorn) اجرا شود.
- پیش از Commit کردن مخزن، از عدم وجود هرگونه کلید، توکن یا آدرس وب‌هوک حساس در تاریخچه Git اطمینان حاصل کنید؛ در صورت افشای قبلی، کلیدها را باطل و مقادیر جدید صادر کنید.
